# Архитектура

## Принятое решение

Сайт работает как традиционное WordPress-приложение с серверным HTML. Headless-архитектура не используется: она не даёт проекту достаточных преимуществ, но потребовала бы отдельного Node.js-хостинга.

Production-окружение:

- Timeweb Optimo;
- WordPress;
- PHP 8.3;
- MySQL 8.0;
- HTTPS;
- почта через SMTP/TLS.

WordPress и все проектные зависимости должны оставаться бесплатными. Затраты на существующий хостинг, домен и почту не считаются лицензией CMS.

Локальное окружение фиксирует MySQL 8.0.46 для соответствия текущей конфигурации Timeweb. Эта ветка MySQL достигла EOL в апреле 2026 года; до production-запуска необходимо отдельно проверить доступность MySQL 8.4 LTS на хостинге и согласовать обновление архитектуры. До этого нельзя молча расходиться с production по версии базы.

## Владение кодом

### Тема `orlyata`

Тема отвечает только за представление:

- PHP-шаблоны страниц;
- компонентные template parts;
- CSS и клиентский TypeScript;
- подключение шрифтов и визуальных assets;
- изображения размеров, зависящих от представления.

Предлагаемая структура:

```text
wp-content/themes/orlyata/
├── assets/
│   ├── src/
│   │   ├── styles/
│   │   └── scripts/
│   └── dist/
├── templates/
├── template-parts/
│   ├── components/
│   └── sections/
├── functions.php
└── style.css
```

### Must-use-плагин `orlyata-core`

Плагин отвечает за данные и бизнес-правила:

- типы контента, taxonomies и meta-поля;
- роли и capabilities;
- настройки контактов и социальных сетей;
- обработку, хранение, отправку и удаление заявок;
- разрешённые типы файлов и очистку SVG;
- миграционные команды;
- редиректы, если они зависят от импортированных данных.

Предлагаемая структура:

```text
wp-content/mu-plugins/
├── orlyata-core.php
└── orlyata-core/
    ├── src/
    │   ├── Content/
    │   ├── Forms/
    │   ├── Migration/
    │   ├── Roles/
    │   └── Settings/
    └── vendor/
```

Корневой loader лежит непосредственно в `mu-plugins`, поскольку WordPress не загружает вложенный каталог MU-плагина автоматически.

## Frontend

- PHP рендерит начальный и основной HTML.
- Vite собирает TypeScript и CSS локально; Node.js на Timeweb не требуется.
- CSS Custom Properties являются интерфейсом дизайн-токенов; плавное масштабирование задаётся только семантическими `rem`-токенами через `clamp()`, а `html` сохраняет `font-size: 100%`.
- CSS разделён на foundations, layout, components, sections и utilities с минимальным набором осознанных utilities. В `styles/components/` каждый production-компонент владеет отдельным CSS-файлом; `main.css` подключает их в документированном порядке каскада.
- Tailwind и CSS-in-JS не используются.
- JavaScript добавляет только меню, фильтры с улучшенным UX, галереи, форму и прочий интерактив. Ссылки, контент, поиск и скачивание имеют серверный fallback.
- `TT Turns Trial` используется с начала вёрстки и размещается локально в WOFF2.

Storybook работает только как локальный каталог токенов и изолированных компонентов. В нём не создаются и не поддерживаются полноценные страницы или page-level preview-экраны. Он использует те же CSS и TypeScript, что тема WordPress; production-разметка остаётся PHP-шаблонами, а React не становится зависимостью публичного сайта.

Каждый визуальный компонент и экран реализуется через Figma MCP: сначала запрашиваются контекст выбранного node, screenshot и исходные assets, затем результат переводится в PHP/CSS/TypeScript проекта и сравнивается с Figma. Код из Figma не копируется как отдельный frontend-стек.

## CMS и редакторская безопасность

- Типы контента и поля регистрируются кодом.
- Для сотрудников создаётся роль `content_editor` с минимальными capabilities.
- Меню админки скрывается не только визуально: запрещённые действия блокируются capability checks.
- Не используются универсальные page builder и неограниченный `post_content` там, где данные структурированы.
- Для новостей разрешается только утверждённый набор блоков/форматирования.
- Удаление media проверяет связи, чтобы редактор не ломал опубликованные страницы.
- SVG проходит серверную очистку; скрипты, event handlers и внешние ссылки внутри SVG удаляются.

## Поиск и фильтры

Для текущего объёма внешний поисковый сервис не нужен.

- Ноты ищутся серверным запросом по названию и автору.
- Хор хранится как закрытая taxonomy или enum-подобное значение.
- Поиск и фильтр используют GET-параметры, совместимы друг с другом и имеют server-rendered empty state.
- Новостной фильтр работает по закрытой taxonomy категорий.
- После миграции должны быть добавлены подходящие индексы для полей, участвующих в поиске и сортировке.

## Файлы и медиа

- Оригиналы фотографий хранятся в WordPress uploads на диске Timeweb; перед стартом переноса проверяется фактический объём архива относительно квоты тарифа.
- WordPress создаёт только заранее определённые размеры изображений.
- На frontend используются `srcset`, `sizes`, WebP/AVIF при поддержке окружением и размеры `width`/`height`.
- PDF проверяется по MIME, расширению и размеру; имя файла не используется как HTML.
- Видео хранится как внешний URL с allowlist поддержанных провайдеров. Провайдер определяется серверным адаптером по нормализованному URL, а не выбирается редактором вручную.
- Для видео хранится смещение начала превью в секундах. Карточка лениво загружает внешний плеер только после взаимодействия; поддержка offset и preview является возможностью конкретного адаптера, поэтому всегда существует статичный fallback.
- Фотоальбомы и видео используют общий закрытый набор категорий: `Выступления`, `Занятия`, `Отдых`, `Разное`.
- Запросы главной и медиагалереи выбирают последние добавленные опубликованные записи по дате создания/публикации; обычное редактирование не поднимает старый материал наверх.
- Резервная копия должна включать базу и uploads; наличие provider backup не отменяет проверяемую копию перед релизом и миграцией.

## Формы и персональные данные

Поток заявки:

```text
браузер → валидация/nonce/rate limit → запись в CMS → SMTP двум адресатам → экран успеха
```

- Сохранение в CMS выполняется до отправки email, чтобы временная ошибка почты не потеряла заявку.
- Повторная отправка письма идемпотентна и доступна только администратору.
- В логах разрешены ID заявки, время, код результата и техническая причина без значений полей.
- Ежедневная WP-Cron-задача удаляет заявки, которым исполнилось 3 года. Для надёжности системный Cron Timeweb вызывает WP-Cron по расписанию.
- Email-адреса получателей являются конфигурацией проекта; SMTP-логин и пароль — секретами окружения.

## Качество и безопасность

Планируемый набор проверок после инициализации кода:

- PHP_CodeSniffer с WordPress Coding Standards;
- PHPStan на согласованном уровне;
- ESLint и TypeScript strict;
- Stylelint;
- unit/integration tests для прав, заявок, срока хранения и миграции;
- Playwright для критичных пользовательских сценариев и responsive smoke tests;
- axe для автоматической части accessibility-проверок;
- production build без ошибок и предупреждений, относящихся к проекту.

Точные команды добавляются в README только одновременно с рабочей конфигурацией.

## Окружения и релиз

1. Создать Git-репозиторий до начала реализации.
2. Разрабатывать на текущем workspace-сервере `89.125.120.78` в воспроизводимом Docker-окружении.
3. Публиковать workspace staging только через Nginx на `80/443`. Сайт, WordPress и Storybook доступны для внешней визуальной проверки; Nginx отдаёт `noindex`, а WordPress имеет `blog_public=0`. Mailpit остаётся закрыт HTTPS Basic Auth, а доступ к WordPress защищён его собственной авторизацией; Docker-порты WordPress, Mailpit и Vite напрямую не открывать.
4. Перед production-запуском развернуть отдельный pre-production staging на Timeweb, в отдельном каталоге и отдельной базе; запретить индексацию и закрыть доступ.
5. Настроить повторяемый импорт Bitrix и проверить данные на pre-production staging.
6. Собрать карту старых и новых URL, проверить редиректы.
7. Перед переключением сделать резервную копию файлов и базы старого сайта.
8. Выполнить финальный импорт изменений, smoke tests, затем переключить production.
9. Сохранить старую систему в закрытом архиве на согласованный срок отката.

Нельзя разрабатывать поверх действующего production-сайта или использовать его базу как тестовую.
