# План реализации

Статус: зафиксирован 10 августа 2026 года. План меняется только вместе с соответствующими решениями в `project.md`, `architecture.md` и дизайн-системе.

## Принципы выполнения

- Сначала контракт дизайн-системы и Storybook, затем страницы.
- Каждый визуальный компонент и экран собирается через Figma MCP по конкретному node, а не по памяти или одному общему скриншоту.
- Production остаётся серверным WordPress: PHP-разметка, CSS и TypeScript с progressive enhancement.
- Storybook — локальный стенд тех же CSS и TypeScript, а не второй production-frontend; в нём живут только foundations (токены) и изолированные компоненты. Полноценные страницы и page-level preview-экраны в Storybook не верстаются и не поддерживаются.
- Адаптив имеет три режима: desktop `1280–2560+`, tablet `768–1279`, mobile `320–767`.
- `1920 px` — точка точного сравнения с десктопным макетом; после неё интерфейс контролируемо растягивается до `2560 px`.
- Desktop fluid scale главной задаётся утверждёнными `clamp()`-токенами и единым коэффициентом: `1280 px → 66.6667%`, `1920 px → 100%`, `2560 px → 133.3333%`. Shell, canvas, компоненты и внутренности используют одну шкалу; minimum gutter `24px` и interaction target `48px` являются явными нижними границами.
- Обязательная визуальная матрица: `2560`, `1920`, `1280`, `1279`, `768`, `767`, `320 px`; для desktop fluid-scale дополнительно выполняется smoke на `1440`, `1600`, `2240 px`. Отдельного viewport `375 px` нет.
- F37 Ginger Cyrillic используется с начала вёрстки.

## Этап 5. Страницы через Figma MCP

### 5.1. Сначала — видимый frontend главной

Первым результатом этапа является desktop-вёрстка главной (`/`) как цельный экран для согласования визуального направления. Она собирается по конкретному Figma-узлу, его screenshot и assets, использует только подтверждённые токены и уже реализованные компоненты. До согласования frontend допускает контролируемые демонстрационные данные для CMS-сущностей (новости, достижения, медиа); эти данные не становятся содержимым production-шаблона.

В scope входят композиция и все секции главной, общая desktop-оболочка, типографика, изображения, hover/focus-состояния и визуальная сверка на 1920 px. Реальный endpoint заявки, персональные данные и SMTP по-прежнему не входят в этот шаг.

### 5.2. Затем — вёрстка остальных страниц

После согласования frontend главной сверстать остальные маршруты на существующих PHP-компонентах и контролируемых демонстрационных данных: общий shell и навигация; Новости; Ноты; Медиагалерея, Фото и Видео; Педагог; Контакты; «О капелле»; 404. Визуальная итерация и проверки страниц выполняются на production-разметке WordPress; в Storybook добавляются только затронутые изолированные компоненты.

Каждая страница проходит тот же MCP-цикл: design context, screenshot, assets, реализация в проектном стеке, визуальное сравнение и desktop accessibility QA. Контент и навигация доступны без обязательного JavaScript. Desktop собирается до начала отдельного адаптивного прохода этапа 6; tablet/mobile-композиция и её приёмка не повторяются для каждой страницы на этом шаге.

Подключение CMS, WordPress-запросов, реальные данные, интеграции и их состояния откладываются до завершения этапа 6. До этого этапы 5–6 посвящены полной адаптивной вёрстке всех страниц.

### 5.3. Проверки во время визуальных итераций

Пока вёрстка активно корректируется и ещё не согласована, используется быстрый цикл проверки: визуальная сверка только на затронутой контрольной ширине (обычно `1920 px`), Stylelint только при изменении CSS, TypeScript- и PHP-проверки только при изменении соответствующих файлов. Production build выполняется после связанной серии правок, а не после каждого небольшого изменения.

После desktop-согласования страницы выполняются desktop baselines `1280`, `1920`, `2560 px`, smoke `1440`, `1600`, `2240 px`, visual regression и geometry assertions для page-level fluid-scale, проверка отсутствия desktop overflow, семантики, keyboard focus и один axe-прогон страницы. Полная матрица `1279`, `768`, `767`, `320 px`, zoom, длинный русский текст, mobile/tablet overflow и keyboard path выполняются один раз в этапе 6 после утверждения соответствующей композиции.

Полные visual snapshots, состояния и axe общих production-компонентов не повторяются при каждой проверке страницы: они запускаются при изменении самого компонента. Статическая сборка Storybook и проверка опубликованного staging-экрана выполняются после изменения production-компонента; production build остаётся обязательным перед завершением связанной серии правок. Production-компоненты, Storybook stories и профильные проверки приводятся к parity в рамках изменения компонента.

Критерий выхода: главная сначала визуально согласована как frontend; затем все маршруты свёрстаны на реальных компонентах и контролируемых демонстрационных данных. CMS-интеграция, реальные данные и состояния loading/error/empty не входят в этап 5 и планируются после этапа 6.

## Этап 6. Tablet и mobile дизайн в коде

1. На базе desktop-компонентов собрать tablet/mobile варианты изолированных компонентов в Storybook.
2. Проектировать смену композиции на границах 1280 и 768 px, а не пропорционально уменьшать desktop. Во всех трёх режимах соблюдать один документированный коэффициент внутри режима: desktop S = clamp(1280/1920, width/1920, 2560/1920), tablet Sₜ = clamp(768/1279, width/1279, 1) и mobile Sₘ = clamp(320/767, width/767, 1). Shell, canvas, типографика, section rhythm, компоненты и их внутренности следуют коэффициенту своего режима; component-owned ratio и внутренняя геометрия сохраняются. Исключения: минимум 24 px outer gutter, 48 px interaction target, hairline, безразмерный line-height, цвета, opacity и full-radius. Без обрезания текста и горизонтального page overflow.
3. Выполнять page-level приёмку последовательно, по одной странице. Для каждой принятой страницы обязательны: матрица `2560`, `1920`, `1280`, `1279`, `768`, `767`, `320 px`; desktop-smoke `1440`, `1600`, `2240 px`; длинный русский текст, зоны нажатия, таблицы, меню, zoom 200%, отсутствие горизонтального скролла, keyboard path, axe и visual regression. После успешной проверки страница отмечается в реестре ниже как «принята».
4. Согласовать варианты и обновить токены/контракты до сборки страниц; при изменении изолированного production-компонента пересобрать Storybook и проверить его staging.

Критерий выхода: все используемые страницами компоненты и страницы имеют утверждённое и проверенное поведение в трёх режимах без дублирования полной mobile/tablet-приёмки на desktop-first этапе.

## Этап 6.1. CMS и интеграции страниц

1. Заменить контролируемые fixtures безопасным server-rendered выводом WordPress для всех страниц этапа 5.2.
2. Подключить WordPress-запросы, навигацию, общие настройки и реальные медиаданные в границах существующей контентной модели.
3. Реализовать и проверить empty/error-состояния, а loading — только там, где он применим к интерактивному клиентскому улучшению.
4. Добавить или актуализировать проверки интегрированных страниц на production-разметке WordPress; page-level Storybook-истории не создаются.

Форма заявки, персональные данные, SMTP и связанные с ними интеграции остаются в этапе 7.

Критерий выхода: все свёрстанные маршруты используют реальные безопасные данные WordPress; fixtures больше не участвуют в production-шаблонах.


## Этап 7. Форма и персональные данные

1. Перед реализацией финального элемента согласия закрыть юридический вопрос о тексте и checkbox.
2. Реализовать nonce, server-side validation, honeypot/антиспам, rate limit и идемпотентность.
3. Сохранять заявку до SMTP-отправки; предоставить root-администратору безопасную повторную отправку.
4. Настроить удаление через 3 года и исключить персональные данные из логов и Яндекс.Метрики.

Критерий выхода: права, доставка, повторная отправка и удаление покрыты тестами; контент-редактор не видит заявки.

## Этап 8. Миграция, SEO и аналитика

1. Инвентаризировать старые URL, сущности и файлы.
2. Реализовать повторяемый импорт Bitrix с dry run и журналом без персональных данных.
3. Подготовить точную карту 301, а для удалённого контента — релевантные 404/410.
4. Настроить metadata, sitemap, robots.txt и Яндекс.Метрику с выбранным режимом согласия.

Критерий выхода: количества, файлы, связи и выборочная сверка контента подтверждены; redirects протестированы.

## Этап 9. Staging, QA и запуск

1. Развернуть закрытый staging на Timeweb.
2. Выполнить production build, lint, static analysis, automated tests, Playwright, axe и ручную проверку матрицы ширин.
3. Проверить резервную копию и сценарий отката.
4. Выполнить финальный импорт и переключение production.

Критерий выхода: критические дефекты отсутствуют, редакторы обучены, backup и rollback проверены.
