# Правила проекта «Орлята»

## Контекст

Проект — русскоязычный корпоративный сайт Хоровой капеллы мальчиков «Орлята». Основные пользователи: родители мальчиков 5–17 лет, журналисты и организаторы, поклонники и выпускники.

Перед началом работы прочитайте:

- `docs/plan.md`
- `docs/project.md`
- `docs/architecture.md`
- `docs/design-system/manifest.json`
- `docs/design-system/design-system.md`
- `docs/design-system/component-map.md`

Не начинайте визуальную реализацию, пока относящиеся к задаче решения не отражены в дизайн-системе.

## Обязательный порядок работы

1. Определить затронутые страницы, контентные сущности и компоненты.
2. Свериться с Figma и документами проекта. Помнить, что макеты пока не pixel-perfect и содержат открытые вопросы.
3. Переиспользовать существующий токен или компонент. Если его недостаточно — сначала обновить контракт дизайн-системы, затем код.
4. Реализовать серверную разметку и поведение с progressive enhancement; основное содержимое и навигация не должны зависеть от JavaScript.
5. Проверить состояния default, hover, focus-visible, active, disabled, loading, success и error там, где они применимы.
6. Для desktop-first задачи проверить `1280`, `1920`, `2560 px` и desktop-smoke `1440`, `1600`, `2240 px`; проверить клавиатурную навигацию и переполнение текста в затронутом режиме. Полную матрицу `2560`, `1920`, `1280`, `1279`, `768`, `767`, `320 px`, zoom и проверки tablet/mobile выполнять при завершении отдельного адаптивного прохода или задачи, меняющей эти режимы.
7. Запустить доступные lint, static analysis, tests и production build. Не объявлять задачу завершённой без проверки затронутого интерфейса.

## Архитектурные ограничения

- Production: WordPress на Timeweb Optimo, PHP 8.3, MySQL 8.0, HTTPS.
- Внешний вид принадлежит только собственной теме `orlyata`.
- Контентная модель, роли, права, заявки, сроки хранения и миграционная логика принадлежат только проектному must-use-плагину `orlyata-core`.
- Не изменять WordPress Core и файлы сторонних пакетов.
- Не использовать Elementor, WPBakery, Divi, готовые темы и другие визуальные конструкторы.
- Не вводить платные плагины или облачные SaaS-зависимости без явного согласования.
- Не хранить критичную бизнес-логику в теме: смена темы не должна удалять типы контента или данные.
- Не регистрировать типы контента и поля через плагины с конфигурацией только в базе; схема должна быть версионируемой в коде.
- На production не нужны Node.js и исходники сборки: загружаются собранные CSS/JS и PHP-код.

## Код и разметка

- PHP следует WordPress Coding Standards; весь вывод экранируется, весь ввод валидируется и очищается.
- JavaScript пишется на TypeScript в strict-режиме и используется только для необходимого интерактива.
- HTML семантический: корректная иерархия заголовков, landmarks, настоящие ссылки и кнопки.
- CSS организуется по токенам и компонентам. Использовать CSS Custom Properties и предсказуемые компонентные классы.
- Запрещены Tailwind, CSS-in-JS, inline-стили, `!important` без документированной причины и случайные числовые значения вне токенов.
- Запрещены CSS media feature и JavaScript-проверки системной настройки сокращения движения: утверждённые анимации не должны от неё зависеть.
- Контент, которым управляет CMS, нельзя дублировать или жёстко прописывать в шаблонах.
- Статические тексты главной и страницы «О капелле» меняются через код и проходят обычный review.
- Для статических preview-экранов текст, подписи и CTA берутся только из утверждённого Figma-узла или проектных контентных документов. Нельзя придумывать, сокращать или перефразировать текст ради заполнения макета.

Визуальный слой защищён дизайн-системой. Она является источником истины для цветов, типографики, интервалов, компонентов, сетки, адаптива, состояний и visual QA:

- `docs/design-system/manifest.json`
- `docs/design-system/design-system.md`
- `docs/design-system/component-map.md`
- `docs/design-system/tokens.css`
- `docs/design-system/screenshots/`
- `docs/desktop-fluid-scaling-audit.md` — измерения и trace решений; нормативные значения остаются в manifest и текстовом контракте.

Не вводить новые визуальные токены, варианты компонентов, градиенты, брейкпоинты или паттерны компоновки, пока они не добавлены в контракт дизайн-системы.

## Storybook parity

Storybook используется только для foundations (токенов) и изолированных production-компонентов: не верстать и не поддерживать в нём полноценные страницы или page-level preview-экраны. Страницы проверяются в production-разметке WordPress на соответствующем staging-экране.

Любое изменение production-компонента обязательно одновременно отражается в его Storybook stories и профильных проверках. Перед завершением такой задачи нужно пересобрать статический Storybook и проверить опубликованный staging-экран.

## Адаптив

- Поддерживаются три режима: desktop `1280–2560+`, tablet `768–1279`, mobile `320–767`.
- `1920 px` — целевая ширина десктопного макета. В диапазоне `1280–2560 px` вся desktop-композиция использует единый коэффициент `S`: `66.6667%` на 1280, `100%` на 1920 и `133.3333%` на 2560. Шире `2560 px` значения не растут, основная композиция центрируется, а полноширинные фоны могут продолжаться.
- Корневой размер шрифта остаётся `100%`; запрещено масштабировать весь интерфейс изменением `html { font-size }`.
- Размеры текста, компонентов, отступы и радиусы задаются в `rem`. `vw` допустим только внутри контролируемого `clamp()` для плавной интерполяции.
- Shell, editorial canvas, типографика, секции, компоненты и их внутренности масштабируются одним `S`. Ширина и высота пропорционального блока не получают независимые fluid-кривые.
- Страница владеет размещением и доступной шириной компонента, но не переопределяет его aspect ratio, внутреннюю геометрию или типографику. Новый ratio сначала оформляется как вариант компонентного контракта.
- Явные исключения: hairline `1px`, безразмерный line-height, цвета, opacity, full-radius, minimum gutter `24px`, minimum interaction target `48px` и документированный viewport-height Hero. Исключения не меняют ratio карточек и крупных секций.
- Медиазапросы задаются в `px`; `1px` допустим для hairline-границ.
- На границах режимов компонент может менять структуру, а не только размер.
- Не добавлять промежуточные глобальные брейкпоинты для локального исправления макета.
- Не обрезать текст и не уменьшать зоны нажатия ради геометрического сходства с десктопом.
- Desktop page-level baselines записываются на 1280, 1920 и 2560 px; smoke на 1440, 1600 и 2240 px проверяет монотонность шкалы, постоянство ratio, отсутствие page-overrides и горизонтального overflow. Изолированная component story не заменяет проверку страницы.

## Контент, SEO и миграция

- Сохранять старые URL, где это возможно. Для изменённых и удалённых адресов поддерживать явную карту 301-редиректов.
- Не перенаправлять все удалённые страницы на главную; выбирать ближайшую релевантную страницу или отдавать честный 410/404.
- Фильтры и поиск отражаются в URL и работают после перезагрузки страницы.
- Изображения получают необходимые размеры и современные форматы; не загружать оригинал во всех контекстах.
- Встраиваемое видео остаётся внешним; не загружать видеофайлы в WordPress без отдельного решения.

## Персональные данные и безопасность

- Заявки видит только учётная запись владельца с ролью администратора. Контент-редакторы доступа не имеют.
- Срок хранения заявки в CMS — 3 года с момента отправки, после чего она удаляется автоматической задачей.
- Полные данные отправляются только на `info@zelorlyata.ru` и `karpman61@rambler.ru` через SMTP/TLS.
- Персональные данные запрещено помещать в тему письма, URL, аналитику, клиентские логи, server logs и сообщения об ошибках.
- Секреты SMTP, salt-ключи и доступы не коммитятся.
- Формы защищаются nonce, honeypot/антиспамом и rate limit; сообщения об ошибках не раскрывают внутреннее устройство системы.
- SVG допускается только после серверной очистки; произвольный SVG/HTML/JavaScript от редакторов запрещён.
- Яндекс.Метрика не получает значения полей формы и не записывает взаимодействия с персональными данными.

## Роли

- `administrator` — владелец проекта: полный доступ, включая заявки и системные настройки.
- `content_editor` — сотрудники капеллы: только создание и изменение разрешённого контента и общих контактов; без плагинов, тем, пользователей, кода, заявок и системных настроек.
